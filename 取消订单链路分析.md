# 取消订单链路深度分析

## 为什么取消订单不是简单地修改 `order.status`

在 Medusa 系统中，取消订单是一个涉及多个模块协调的复杂业务流程，而不仅仅是修改订单状态字段。这是因为：

1. **订单与多个实体关联**：订单关联了支付、库存预订、履约、支付集合等多个实体
2. **需要保证数据一致性**：取消订单时需要同步更新所有关联实体的状态
3. **需要处理资金流**：涉及支付退款、信用额度创建等资金相关操作
4. **需要支持事务回滚**：工作流中的每个步骤都需要有补偿机制，确保失败时能够回滚

---

## 一、取消前的校验逻辑

在执行任何取消操作之前，系统会进行严格的前置校验，确保订单处于可取消状态。

### 1.1 校验入口

校验逻辑定义在 `cancelValidateOrder` 步骤中：

**文件位置**: `packages/core/core-flows/src/order/workflows/cancel-order.ts:70-104`

```typescript
export const cancelValidateOrder = createStep(
  "cancel-validate-order",
  ({ order }: CancelValidateOrderStepInput) => {
    const order_ = order as OrderDTO & {
      payment_collections: PaymentCollectionDTO[]
      fulfillments: FulfillmentDTO[]
    }

    throwIfOrderIsCancelled({ order })

    if (order.status === OrderStatus.COMPLETED) {
      throw new MedusaError(
        MedusaError.Types.NOT_ALLOWED,
        `Cannot cancel a completed order. Please use the return process to handle refunds or exchanges.`
      )
    }

    const throwErrorIf = (
      arr: unknown[],
      pred: (obj: any) => boolean,
      type: string
    ) => {
      if (arr?.some(pred)) {
        throw new MedusaError(
          MedusaError.Types.NOT_ALLOWED,
          `All ${type} must be canceled before canceling an order`
        )
      }
    }

    const notCanceled = (o) => !o.canceled_at

    throwErrorIf(order_.fulfillments, notCanceled, "fulfillments")
  }
)
```

### 1.2 具体校验项

| 校验项 | 校验逻辑 | 错误类型 | 错误信息 |
|--------|----------|----------|----------|
| 订单是否已取消 | `order.status === OrderStatus.CANCELED` | `INVALID_DATA` | `Order with id ${order.id} has been canceled.` |
| 订单是否已完成 | `order.status === OrderStatus.COMPLETED` | `NOT_ALLOWED` | `Cannot cancel a completed order. Please use the return process to handle refunds or exchanges.` |
| 所有履约是否已取消 | `fulfillments.some(f => !f.canceled_at)` | `NOT_ALLOWED` | `All fulfillments must be canceled before canceling an order` |

### 1.3 订单状态查询

在校验之前，系统会通过 `useQueryGraphStep` 查询订单的详细信息，包括：

**查询字段**:
- `id` - 订单ID
- `status` - 订单状态
- `items.id` - 订单项ID
- `fulfillments.canceled_at` - 履约取消时间
- `payment_collections.payments.id` - 支付集合中的支付ID
- `payment_collections.payments.amount` - 支付金额
- `payment_collections.payments.refunds.*` - 退款信息
- `payment_collections.payments.captures.*` - 捕获信息

**文件位置**: `packages/core/core-flows/src/order/workflows/cancel-order.ts:136-154`

## 二、取消过程中的并行子流程

通过校验后，系统会并行触发多个子流程，提高处理效率。

### 2.1 并行执行的步骤

**文件位置**: `packages/core/core-flows/src/order/workflows/cancel-order.ts:181-191`

```typescript
const [refundedPayments] = parallelize(
  refundCapturedPaymentsWorkflow.runAsStep({

  cancelPaymentStep({ paymentIds: uncapturedPaymentIds }),
  emitEventStep({
    eventName: OrderWorkflowEvents.CANCELED,
    data: { id: order.id },
  })

```

### 2.2 各子流程详细说明

#### 2.2.1 退款已捕获的支付 (`refundCapturedPaymentsWorkflow`)

**职责**: 对已经捕获（captured）的支付进行退款处理

**文件位置**: `packages/core/core-flows/src/order/workflows/payments/refund-captured-payments.ts`

**处理逻辑**:
1. 查询订单的支付集合和支付信息
2. 筛选出有捕获记录的支付 (`payment.captures?.length > 0`)
3. 计算每个支付需要退款的金额：`已捕获金额 - 已退款金额`
4. 调用 `refundPaymentsWorkflow` 执行实际退款

**核心计算**:
```typescript
const capturedAmount = (payment.captures || []).reduce(
  (acc, capture) => MathBN.sum(acc, capture.amount),
  MathBN.convert(0)
)
const refundedAmount = (payment.refunds || []).reduce(
  (acc, refund) => MathBN.sum(acc, refund.amount),
  MathBN.convert(0)
)
const amountToRefund = MathBN.sub(capturedAmount, refundedAmount)
```

#### 2.2.2 删除库存预订 (`deleteReservationsByLineItemsStep`)

**职责**: 删除与订单项关联的库存预订，释放库存

**文件位置**: `packages/core/core-flows/src/reservation/steps/delete-reservations-by-line-items.ts:16-33`

**处理逻辑**:
```typescript
export const deleteReservationsByLineItemsStep = createStep(
  deleteReservationsByLineItemsStepId,
  async (ids: DeleteReservationsByLineItemsStepInput, { container }) => {
    const service = container.resolve<IInventoryService>(Modules.INVENTORY)
    await service.deleteReservationItemsByLineItem(ids)
    return new StepResponse(void 0, ids)
  },
  async (prevIds, { container }) => {
    if (!prevIds?.length) {
      return
    }
    const service = container.resolve<IInventoryService>(Modules.INVENTORY)
    await service.restoreReservationItemsByLineItem(prevIds)
  }
)
```

**补偿机制**: 如果工作流失败，会通过 `restoreReservationItemsByLineItem` 恢复预订。

#### 2.2.3 取消未捕获的支付 (`cancelPaymentStep`)

**职责**: 取消尚未捕获（uncaptured）的支付授权

**文件位置**: `packages/core/core-flows/src/payment/steps/cancel-payment.ts:23-48`

**处理逻辑**:
```typescript
export const cancelPaymentStep = createStep(
  cancelPaymentStepId,
  async (input: CancelPaymentStepInput, { container }) => {
    const logger = container.resolve<Logger>(ContainerRegistrationKeys.LOGGER)
    const paymentModule = container.resolve<IPaymentModuleService>(
      Modules.PAYMENT
    )

    const paymentIds = Array.isArray(input.paymentIds)
      ? input.paymentIds
      : [input.paymentIds]

    const promises: Promise<any>[] = []

    for (const id of paymentIds) {
      promises.push(
        paymentModule.cancelPayment(id).catch((e) => {
          logger.error(
            `Error was thrown trying to cancel payment - ${id} - ${e}`
          )
        })
      )
    }

    await promiseAll(promises)
  }
)
```

**特点**: 
- 使用 `promiseAll` 并行取消多个支付
- 单个支付取消失败不会阻止其他支付的取消（使用 `.catch()` 吞掉错误并记录日志）
- 未捕获的支付通常是授权（authorized）状态，需要释放授权额度

#### 2.2.4 发送订单取消事件 (`emitEventStep`)

**职责**: 发布 `OrderWorkflowEvents.CANCELED` 事件，通知系统其他组件订单已取消

**事件名称**: `OrderWorkflowEvents.CANCELED`

**事件数据**: `{ id: order.id }`

**用途**: 
- 允许订阅者监听订单取消事件
- 触发异步处理（如发送通知、更新统计等）

## 三、各模块的具体动作

取消订单涉及多个模块的协调操作，每个模块负责处理自己领域内的逻辑。

### 3.1 Order 模块（订单模块）

**核心职责**: 更新订单状态为已取消

**文件位置**: `packages/modules/order/src/services/order-module-service.ts:4144-4176`

**实现逻辑**:
```typescript
@InjectTransactionManager()
private async cancel_(
  orderId: string | string[],
  @MedusaContext() sharedContext: Context = {}
): Promise<OrderTypes.OrderDTO[]> {
  const orderIds = Array.isArray(orderId) ? orderId : [orderId]
  const orders = await this.listOrders_(
    { id: orderIds },
    {},
    sharedContext
  )

  const canceled_at = new Date()
  for (const order of orders) {
    order.status = OrderStatus.CANCELED
    order.canceled_at = canceled_at
  }

  await this.orderService_.update(
    orderIds.map((id) => {
      return {
        id,
        status: OrderStatus.CANCELED,
        canceled_at,
      }
    }),
    sharedContext
  )

  return orders
}
```

**更新的字段**:
- `status`: 设置为 `OrderStatus.CANCELED`
- `canceled_at`: 设置为当前时间

**调用时机**: 在所有并行子流程和后续步骤完成后，通过 `cancelOrdersStep` 调用。

### 3.2 Payment 模块（支付模块）

**核心职责**: 处理支付相关操作

**涉及的操作**:

| 操作类型 | 触发条件 | 实现位置 |
|----------|----------|----------|
| 取消未捕获支付 | 支付没有捕获记录 | `cancelPaymentStep` |
| 退款已捕获支付 | 支付有捕获记录且有未退款金额 | `refundCapturedPaymentsWorkflow` |

**取消未捕获支付的调用链**:
```
cancelPaymentStep → IPaymentModuleService.cancelPayment(paymentId)
```

**退款已捕获支付的调用链**:
```
refundCapturedPaymentsWorkflow → refundPaymentsWorkflow → 实际退款操作
```

### 3.3 Reservation 模块（库存预订模块）

**核心职责**: 管理库存预订

**文件位置**: `packages/core/core-flows/src/reservation/steps/delete-reservations-by-line-items.ts`

**调用链**:
```
deleteReservationsByLineItemsStep → IInventoryService.deleteReservationItemsByLineItem(lineItemIds)
```

**补偿操作**:
```
restoreReservationItemsByLineItem(prevIds)
```

**业务意义**: 订单取消后，需要释放之前为该订单保留的库存，以便其他订单可以使用。

### 3.4 Payment Collection 模块（支付集合模块）

**核心职责**: 更新支付集合的状态

**文件位置**: `packages/core/core-flows/src/order/workflows/cancel-order.ts:247-254`

**实现逻辑**:

## 四、其他关键步骤

### 4.1 创建退款信用额度 (`createOrderRefundCreditLinesWorkflow`)

**文件位置**: `packages/core/core-flows/src/order/workflows/cancel-order.ts:236-241`

**触发时机**: 在并行子流程完成后，更新支付集合状态之前

**业务逻辑**:
1. 计算实际新增的退款金额：`本次退款金额 - 之前已退款金额`
2. 创建订单信用额度记录，用于跟踪退款金额

**核心计算**:
```typescript
const creditLineAmount = transform(
  { order, refundedPaymentIds, refundedPaymentRefundsQuery },
  ({ order, refundedPaymentIds, refundedPaymentRefundsQuery }) => {
    const refundedIds = new Set(refundedPaymentIds)

    const totalRefundedAfter = refundedPaymentRefundsQuery.data.reduce(
      (acc, refund) => MathBN.sum(acc, refund.raw_amount),
      MathBN.convert(0)
    )

    const totalRefundedBefore = deepFlatMap(
      order,
      "payment_collections.payments",
      ({ payments }) => payments
    )
      .filter((payment) => refundedIds.has(payment.id))
      .reduce(
        (acc, payment) =>
          (payment.refunds || []).reduce(
            (inner, refund) =>
              MathBN.sum(inner, refund.raw_amount ?? refund.amount),
            acc
          ),
        MathBN.convert(0)
      )

    return MathBN.sub(totalRefundedAfter, totalRefundedBefore)
  }
)
```

## 五、为什么最后要重新 `remoteQuery` 一次订单

在 API 路由的最后，系统会通过 `remoteQuery` 重新查询订单并返回给调用方。

### 5.1 API 路由实现

**文件位置**: `packages/medusa/src/api/admin/orders/[id]/cancel/route.ts:12-38`

```typescript
export const POST = async (
  req: AuthenticatedMedusaRequest<{}, HttpTypes.AdminGetOrderParams>,
  res: MedusaResponse<HttpTypes.AdminOrderResponse>
) => {
  const remoteQuery = req.scope.resolve(ContainerRegistrationKeys.REMOTE_QUERY)

  const variables = { id: req.params.id }

  const input = {
    order_id: req.params.id,
    canceled_by: req.auth_context.actor_id,
  }

  await cancelOrderWorkflow(req.scope).run({
    input,
  })

  const queryObject = remoteQueryObjectFromString({
    entryPoint: "order",
    variables,
    fields: req.queryConfig.fields,
  })

  const [order] = await remoteQuery(queryObject)

  res.status(200).json({ order })
}
```

### 5.2 重新查询的原因

#### 原因一：工作流中查询的字段有限

工作流中的查询只获取了执行取消操作所需的最小字段集：

**工作流查询字段**:
```typescript
fields: [
  "id",
  "status",
  "items.id",
  "fulfillments.canceled_at",
  "payment_collections.payments.id",
  "payment_collections.payments.amount",
  "payment_collections.payments.refunds.id",
  "payment_collections.payments.refunds.amount",
  "payment_collections.payments.refunds.raw_amount",
  "payment_collections.payments.captures.id",
  "payment_collections.payments.captures.amount",
  "payment_collections.payments.captures.raw_amount",
]
```

这些字段不足以构成完整的订单响应。

#### 原因二：API 调用方可能需要自定义字段

通过 `req.queryConfig.fields`，调用方可以指定需要返回的字段：

```typescript
const queryObject = remoteQueryObjectFromString({
  entryPoint: "order",
  variables,
  fields: req.queryConfig.fields,  // 调用方指定的字段
})
```

这样调用方可以根据自己的需求获取完整或部分订单数据。

#### 原因三：确保数据的最新性和一致性

取消订单过程中，多个模块的数据都发生了变化：
- 订单状态更新
- 支付状态变更
- 退款记录创建
- 支付集合状态更新

通过 `remoteQuery` 重新查询，可以确保：
1. **获取完整的关联数据**: 包括支付、退款、信用额度等
2. **数据一致性**: 所有模块的更新都已完成
3. **支持 GraphQL 风格的字段选择**: 调用方可以灵活选择需要的字段

#### 原因四：模块化架构的最佳实践

Medusa 采用模块化架构，`remoteQuery` 是跨模块查询数据的标准方式：

1. **解耦**: API 层不需要直接依赖各个模块的内部实现
2. **统一查询接口**: 通过 `remoteQuery` 可以查询任何模块的数据
3. **支持字段级选择**: 符合现代 API 设计最佳实践

## 八、设计要点总结

### 8.1 工作流设计优势

1. **可组合性**: 通过 `createStep` 和 `parallelize` 可以灵活组合业务逻辑
2. **事务支持**: 每个步骤都可以定义补偿函数，支持工作流回滚
3. **可扩展性**: 通过 `createHook` 允许开发者插入自定义逻辑
4. **可读性**: 工作流代码清晰地表达了业务流程

### 8.2 模块化设计优势

1. **职责分离**: 每个模块负责自己领域内的逻辑
2. **独立演进**: 模块可以独立开发、测试和部署
3. **松耦合**: 模块之间通过接口和事件通信，不直接依赖内部实现

### 8.3 数据一致性保证

1. **前置校验**: 确保操作在合法状态下执行
2. **工作流事务**: 通过补偿机制保证最终一致性
3. **顺序执行**: 关键操作（如更新订单状态）放在最后执行
4. **事件通知**: 通过事件机制确保异步操作的触发

### 8.4 API 设计最佳实践

1. **字段级选择**: 支持 `fields` 参数，让调用方按需获取数据
2. **统一响应格式**: 返回 `{ order }` 格式，便于扩展
3. **最新数据保证**: 通过重新查询确保返回数据的准确性
4. **模块化查询**: 使用 `remoteQuery` 实现跨模块数据查询

## 九、常见问题解答

### Q1: 为什么已完成的订单不能取消？

**A**: 已完成的订单意味着商品已经交付给客户，此时取消订单不符合业务逻辑。如果需要退款，应该使用退货（return）流程来处理。

**代码位置**: `packages/core/core-flows/src/order/workflows/cancel-order.ts:80-85`

```typescript
if (order.status === OrderStatus.COMPLETED) {
  throw new MedusaError(
    MedusaError.Types.NOT_ALLOWED,
    `Cannot cancel a completed order. Please use the return process to handle refunds or exchanges.`
  )
}
```

### Q2: 为什么必须先取消所有履约才能取消订单？

**A**: 履约（fulfillment）代表商品已经发货或正在发货流程中。如果有未取消的履约，说明商品可能已经发出，此时取消订单会导致业务逻辑混乱。必须先取消所有履约，确保商品不会发出，才能安全地取消订单。

**代码位置**: `packages/core/core-flows/src/order/workflows/cancel-order.ts:99-103`

```typescript
const notCanceled = (o) => !o.canceled_at
throwErrorIf(order_.fulfillments, notCanceled, "fulfillments")
```

### Q3: 为什么支付取消失败不会阻止订单取消？

**A**: 在 `cancelPaymentStep` 中，单个支付取消失败会被捕获并记录日志，但不会抛出异常阻止整个流程。这是因为：
1. 支付网关可能暂时不可用
2. 某些支付可能已经处于无法取消的状态
3. 订单取消是核心业务流程，不应该被支付网关的问题阻塞

**代码位置**: `packages/core/core-flows/src/payment/steps/cancel-payment.ts:37-45`

```typescript

  paymentModule.cancelPayment(id).catch((e) => {
    logger.error(
      `Error was thrown trying to cancel payment - ${id} - ${e}`
    )
  })
)
```

### Q4: 工作流中的步骤执行顺序是怎样的？

**A**: 执行顺序如下：

1. **串行执行**:
   - 查询订单详情
   - 前置校验
   - 创建退款信用额度
   - 更新支付集合状态
   - 更新订单状态
   - 触发取消钩子

2. **并行执行**（在校验之后）:
   - 退款已捕获支付
   - 删除库存预订
   - 取消未捕获支付
   - 发送取消事件

这种设计既保证了关键步骤的顺序性，又通过并行化提高了性能。

### Q5: 如果工作流执行失败会怎样？

**A**: Medusa 的工作流引擎支持补偿机制：

1. **每个步骤都可以定义补偿函数**（如 `deleteReservationsByLineItemsStep` 的第二个参数）
2. **当工作流失败时**，引擎会按相反顺序执行已成功步骤的补偿函数
3. **补偿函数的作用**是将系统状态恢复到工作流执行之前

例如，`deleteReservationsByLineItemsStep` 的补偿函数会恢复已删除的预订：

```typescript
async (prevIds, { container }) => {
  if (!prevIds?.length) {
    return
  }
  const service = container.resolve<IInventoryService>(Modules.INVENTORY)
  await service.restoreReservationItemsByLineItem(prevIds)
}
```

## 十、扩展思考

### 10.1 如何自定义取消订单逻辑？

开发者可以通过以下方式扩展取消订单流程：

1. **使用 Hook**: 订阅 `orderCanceled` hook，在订单取消后执行自定义逻辑
2. **创建自定义工作流**: 基于 `cancelOrderWorkflow` 创建自定义工作流，添加或修改步骤
3. **监听事件**: 订阅 `OrderWorkflowEvents.CANCELED` 事件，执行异步处理

### 10.2 如何处理部分取消？

当前实现只支持完全取消订单。如果需要支持部分取消（取消部分订单项），需要：

1. 创建新的工作流（如 `cancelOrderItemsWorkflow`）
2. 只处理特定订单项的库存预订
3. 计算部分退款金额
4. 更新订单状态为 `PARTIALLY_CANCELED`（如果有此状态）

### 10.3 如何支持不同支付方式的特殊处理？

当前的支付取消逻辑是通用的。如果需要为特定支付方式添加特殊处理：

1. 在支付模块中实现不同的 `cancelPayment` 逻辑
2. 或者在工作流中根据支付方式类型选择不同的步骤
3. 通过事件机制让外部系统处理特定支付方式的取消
